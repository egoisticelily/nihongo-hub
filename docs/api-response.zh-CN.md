# API 响应与错误代码规范

> **文档状态：** 中文草案，待确认  
> **规范版本：** 0.1  
> **适用范围：** NihongoHub 后端 HTTP API  
> **最后更新：** 2026-11-14

本文约定 NihongoHub API 的 HTTP 响应状态码、应用层响应代码及错误信息的使用方式。当前版本以中文说明为准；经确认后，再制作日文和英文版本。

## 1. 设计目标

NihongoHub 使用两套相互独立的状态编码：

- **HTTP Status Code（HTTP 状态码）：** 遵循 HTTP 规范，用于表达 HTTP 请求在协议和资源层面的处理结果。
- **NihongoHub API Code（应用层代码）：** 由 NihongoHub 自行定义，用于识别具体的业务结果、请求问题、认证问题或服务器错误。

两者解决的问题不同，不应混用，也不要求数值相同。

例如，用户提交了错误的登录凭据：

- HTTP 状态码：401 Unauthorized
- API Code：1101（用户名或密码错误）

数据库发生异常时：

- HTTP 状态码：500 Internal Server Error
- API Code：9001（数据库操作失败）

## 2. 响应结构

当前项目使用统一响应结构：

| 字段 | 类型 | 含义 |
|---|---|---|
| success | bool | 本次 API 操作是否成功 |
| code | int | NihongoHub 应用层代码 |
| message | string? | 面向调用者的说明信息 |
| data | 泛型 / 可空 | 本次操作返回的数据 |

### 2.1 HTTP 状态码不属于响应 JSON

HTTP 状态码属于 HTTP 响应本身，而不是响应 Body 中的业务字段。

例如，Minimal API 可以通过 Results.Json(..., statusCode: ...) 设置 HTTP 状态码。响应 JSON 仍然使用 success、code、message 和 data。

因此，本文中的“StatusCode”指真实 HTTP 响应状态，不是要求在 JSON 中增加一个同名字段。

### 2.2 成功响应

应用层成功代码统一使用 **0**。

约定：

- success = true 时，code 必须为 0。
- success = false 时，code 必须为非零值。
- 成功响应的 HTTP 状态码根据操作类型选择，通常使用 200 OK；创建资源时可以使用 201 Created。
- 如果使用 204 No Content，HTTP 响应不应包含 JSON Body。为了保持当前统一响应结构，项目在需要返回响应对象时优先使用 200 或 201。

示例：

~~~json
{
  "success": true,
  "code": 0,
  "message": "登录成功",
  "data": {
    "token": "...",
    "userid": 1,
    "usertype": "admin",
    "expiresat": "..."
  }
}
~~~

对应 HTTP 状态码：200 OK。

### 2.3 失败响应

失败响应使用非零 API Code。通常在无法提供有效业务数据时将 data 设置为 null；对于批量操作或部分成功的场景，是否返回部分结果需要由对应 API 单独约定。

示例：

~~~json
{
  "success": false,
  "code": 1101,
  "message": "用户名或密码错误",
  "data": null
}
~~~

对应 HTTP 状态码：401 Unauthorized。

## 3. API Code 编号规则

应用层代码使用整数（int），按功能模块划分编号区间。编号一经正式使用，其含义不应随意更改；废弃的编号也不应重新分配给其他含义。

| 编号范围 | 类别 | 说明 |
|---|---|---|
| 0 | 成功 | API 操作成功 |
| 1000–1099 | 通用请求错误 | 请求体、JSON、参数及请求格式问题 |
| 1100–1199 | 身份认证错误 | 登录凭据、Token 和当前身份有效性问题 |
| 1200–1299 | 权限错误 | 已识别身份，但无权执行操作或访问资源 |
| 2000–2099 | 用户管理 | 用户数据和用户管理操作相关问题 |
| 3000–3099 | 单词管理 | 单词数据和单词操作相关问题 |
| 4000–4099 | 单词本管理 | 单词本数据和关联操作相关问题 |
| 5000–5099 | 学习与检测 | 学习、答题和检测相关问题，暂留待实现 |
| 9000–9099 | 服务器内部错误 | 数据库、配置和未预期的服务器端问题 |

各区间中未列出的编号暂时保留，后续根据实际功能扩展。

## 4. 当前常见 API Code

以下列表是第一阶段建议使用的代码。尚未实现的业务代码属于预留定义，不代表对应功能已经存在。

### 4.1 通用请求错误（1000–1099）

| Code | 含义 | 建议 HTTP 状态码 | 说明 |
|---:|---|---:|---|
| 1000 | 请求参数无效 | 400 | 参数不符合 API 要求 |
| 1001 | 请求体为空 | 400 | 请求没有提供所需 Body |
| 1002 | JSON 格式错误 | 400 | Body 无法按预期解析为 JSON |
| 1003 | 缺少必要参数 | 400 | 缺少必要字段 |
| 1004 | 参数值不符合要求 | 400 | 字段存在，但值无效 |
| 1005 | 不支持的请求格式 | 415 | 请求的媒体类型或内容格式不受支持 |

### 4.2 身份认证错误（1100–1199）

| Code | 含义 | 建议 HTTP 状态码 | 说明 |
|---:|---|---:|---|
| 1100 | 身份认证失败 | 401 | 通用认证失败代码；能够明确原因时优先使用更具体的代码 |
| 1101 | 用户名或密码错误 | 401 | 登录凭据不正确；用户名不存在和密码错误对外统一使用此代码 |
| 1102 | Token 缺失 | 401 | 受保护的 API 没有收到 Token |
| 1103 | Token 无效 | 401 | Token 签名、格式或其他必要验证不通过 |
| 1104 | Token 已过期 | 401 | Token 已超过有效期 |
| 1105 | Token 尚未生效 | 401 | Token 的生效时间尚未到达 |
| 1106 | Token Claims 无效 | 401 | Token 缺少必要身份信息或 Claims 格式不符合要求 |
| 1107 | 用户身份已失效 | 401 | Token 对应的用户已不存在、被禁用，或数据库中的角色与 Token 不一致 |

补充约定：

- Login 对外不区分“用户名不存在”和“密码错误”，统一返回 1101，避免泄露用户名是否存在。
- 用户被禁用、删除或角色发生变化后，已有 Token 应无法通过当前用户身份验证。对外可以统一使用 1107。
- 数据库查询异常不是认证失败，应使用服务器内部错误代码，而不是 1101 或 1107。

### 4.3 权限错误（1200–1299）

| Code | 含义 | 建议 HTTP 状态码 | 说明 |
|---:|---|---:|---|
| 1200 | 无权执行此操作 | 403 | 当前身份不能执行该操作 |
| 1201 | 需要管理员权限 | 403 | 当前操作要求管理员身份 |
| 1202 | 无权访问该资源 | 403 或 404 | 资源存在，但调用者无权访问；若需要隐藏资源是否存在，可使用 404 |

对于用户私有的单词和单词本，建议在 API 层考虑隐藏资源是否存在，避免用户通过错误响应探测其他用户的数据。具体采用 403 还是 404，应在相关 API 设计中保持一致。

### 4.4 用户管理错误（2000–2099）

| Code | 含义 | 建议 HTTP 状态码 | 说明 |
|---:|---|---:|---|
| 2000 | 用户操作失败 | 根据具体原因 | 通用备用代码；有更具体代码时应优先使用具体代码 |
| 2001 | 用户不存在 | 404 | 用户管理操作中，目标用户不存在 |
| 2002 | 用户名已被使用 | 409 | 创建或修改用户时发生用户名冲突 |
| 2003 | 用户已被禁用 | 409 或 403 | 用户管理场景中，目标用户处于禁用状态 |
| 2004 | 用户数据无效 | 400 | 提交的用户数据不符合要求 |
| 2005 | 不允许执行该用户操作 | 403 | 当前调用者无权管理目标用户 |

注意：登录场景中的账号状态不应直接暴露为 2003，应按照身份认证错误规则处理。

### 4.5 单词管理错误（3000–3099）

| Code | 含义 | 建议 HTTP 状态码 | 说明 |
|---:|---|---:|---|
| 3000 | 单词操作失败 | 根据具体原因 | 通用备用代码；有更具体代码时应优先使用具体代码 |
| 3001 | 单词不存在 | 404 | 目标单词不存在 |
| 3002 | 单词数据无效 | 400 | 提交的单词数据不符合要求 |
| 3003 | 无权操作该单词 | 403 或 404 | 单词存在，但不属于当前用户 |
| 3004 | 单词关联操作失败 | 500 | 操作单词时，维护其关联关系发生服务器端错误 |

### 4.6 单词本管理错误（4000–4099）

| Code | 含义 | 建议 HTTP 状态码 | 说明 |
|---:|---|---:|---|
| 4000 | 单词本操作失败 | 根据具体原因 | 通用备用代码；有更具体代码时应优先使用具体代码 |
| 4001 | 单词本不存在 | 404 | 目标单词本不存在 |
| 4002 | 单词本数据无效 | 400 | 提交的单词本数据不符合要求 |
| 4003 | 无权操作该单词本 | 403 或 404 | 单词本存在，但不属于当前用户 |
| 4004 | 单词本关联操作失败 | 500 | 维护单词与单词本关系时发生服务器端错误 |
| 4005 | 单词与单词本关联已存在 | 409 | 添加关联时发现关系已经存在；是否采用此行为由关联 API 的设计决定 |

### 4.7 学习与检测错误（5000–5099）

该区间暂时保留，待学习和检测功能实现时再正式确定。以下仅作为可能的方向：

| Code | 预留含义 |
|---:|---|
| 5001 | 检测任务不存在 |
| 5002 | 答案格式无效 |
| 5003 | 检测记录不存在 |
| 5004 | 检测任务已经结束 |

以上代码尚未正式启用。

### 4.8 服务器内部错误（9000–9099）

| Code | 含义 | 建议 HTTP 状态码 | 说明 |
|---:|---|---:|---|
| 9000 | 服务器内部错误 | 500 | 无法归入更具体类别的服务器端错误 |
| 9001 | 数据库操作失败 | 500 | 数据库读写或查询发生异常 |
| 9002 | 未知异常 | 500 | 未预期且无法分类的服务器异常 |
| 9003 | 服务器配置错误 | 500 | 服务器配置缺失或不合法 |
| 9004 | 内部业务处理失败 | 500 | 服务器内部处理过程未能完成 |

服务器内部错误不应向客户端暴露数据库路径、异常堆栈、密钥、文件路径或其他内部实现细节。详细信息应记录在服务器日志中。

## 5. HTTP Status Code 使用约定

HTTP 状态码遵循 HTTP 语义。API Code 不直接决定 HTTP 状态码；API 应根据请求实际失败原因选择合适的 HTTP 状态码。

| HTTP 状态码 | 名称 | 常见使用场景 |
|---:|---|---|
| 200 | OK | 请求成功并返回响应内容 |
| 201 | Created | 成功创建资源 |
| 204 | No Content | 请求成功，但不返回响应 Body |
| 400 | Bad Request | 请求体、JSON 或参数不合法 |
| 401 | Unauthorized | 缺少有效身份凭证或认证失败 |
| 403 | Forbidden | 身份已识别，但没有执行操作的权限 |
| 404 | Not Found | 目标资源不存在，或按安全策略隐藏资源存在性 |
| 409 | Conflict | 当前资源状态或唯一性约束产生冲突 |
| 415 | Unsupported Media Type | 请求媒体类型不受支持 |
| 500 | Internal Server Error | 服务器内部发生异常 |

### 5.1 认证与权限的区别

- **401：** 当前请求没有通过身份认证，例如 Token 缺失、无效或过期。
- **403：** 身份已经通过认证，但没有权限执行操作。

例如，普通用户请求管理员专用操作，应返回 403，而不是 401。

### 5.2 资源不存在与无权访问

对于用户私有资源，API 可以根据安全策略选择：

- 返回 403，明确表示资源存在但当前用户无权访问。
- 返回 404，不向调用者透露资源是否存在。

同一类 API 应尽量保持一致。

### 5.3 创建、更新与删除

- 创建资源且返回资源信息：通常使用 201。
- 查询、更新或删除成功并返回统一响应 Body：通常使用 200。
- 操作成功且不需要返回 Body：可以使用 204，但不能同时返回 JSON 响应对象。

## 6. 字段之间的一致性规则

### 6.1 success 与 code

- 成功：success = true 且 code = 0。
- 失败：success = false 且 code != 0。

不能出现成功标志与 API Code 相互矛盾的情况。

### 6.2 code 与 message

- code 是供程序识别的稳定标识，应保持含义固定。
- message 是说明信息，可以根据语言、客户端和使用场景调整。
- 客户端逻辑应根据 code 判断，不应通过解析 message 判断错误类型。
- 不应为了改变文案而更换 API Code。

### 6.3 API Code 与日志分类

项目中的 Logging.LogCategory 用于服务器内部日志分类，例如 Database、Unknown 和 Http。

它与 API Code 是两套不同的体系：

- LogCategory.Database 不等于 API Code 9001。
- 日志分类用于排查问题。
- API Code 用于让客户端识别响应含义。
- API 不应直接把内部日志分类当成 API Code 返回。

### 6.4 错误信息与内部细节

返回给客户端的 message 应只包含调用者需要知道的信息。

数据库异常、堆栈信息、内部文件路径和其他敏感实现细节应保留在服务端日志中。

## 7. 批量操作与部分成功

Word 和 VocabularyNotebook 支持批量操作。批量请求可能出现部分项目成功、部分项目失败的情况。

这类情况不能简单地将整个请求描述为完全成功或完全失败，也不应丢失具体失败项目的信息。

当前规范暂不统一规定批量操作的 HTTP 状态码和 API Code。后续设计对应 API 时，需要单独明确：

- 是否允许部分成功。
- success 表示整个批次成功，还是至少一个项目成功。
- data 如何返回成功项目。
- 失败项目如何返回 ID、API Code 和错误信息。
- 整个批次使用什么 HTTP 状态码。

在这些规则确定前，不应为部分成功场景随意创造或复用错误代码。

## 8. 代码实现建议

建议将 API Code 集中定义为常量，避免在各个 API 处理器中散落难以维护的数字。

例如：

~~~csharp
public static class ApiCode
{
    public const int Success = 0;

    public const int InvalidRequest = 1000;
    public const int RequestBodyEmpty = 1001;
    public const int InvalidJson = 1002;

    public const int InvalidCredentials = 1101;
    public const int TokenMissing = 1102;
    public const int TokenInvalid = 1103;
    public const int TokenExpired = 1104;

    public const int PermissionDenied = 1200;

    public const int UserNotFound = 2001;
    public const int UsernameAlreadyExists = 2002;

    public const int WordNotFound = 3001;
    public const int VocabularyNotebookNotFound = 4001;

    public const int InternalServerError = 9000;
    public const int DatabaseOperationFailed = 9001;
    public const int UnknownError = 9002;
}
~~~

以上仅展示组织方式。实际实现时应按本规范补充所需常量，并保持常量名称、编号和含义一致。

HTTP 状态码建议使用 ASP.NET Core 提供的常量，例如：

~~~csharp
StatusCodes.Status200OK
StatusCodes.Status201Created
StatusCodes.Status400BadRequest
StatusCodes.Status401Unauthorized
StatusCodes.Status403Forbidden
StatusCodes.Status404NotFound
StatusCodes.Status409Conflict
StatusCodes.Status415UnsupportedMediaType
StatusCodes.Status500InternalServerError
~~~

## 9. 当前版本暂不约定的内容

以下内容留待相关功能开发时确定：

- 批量操作部分成功时的统一响应策略。
- 用户私有资源统一采用 403 还是隐藏资源存在性的 404（建议同类 API 保持一致）。
- 具体业务场景是否需要新增更细的 API Code。
- 限流、维护状态等尚未实现的 API 行为及其状态码。

新增代码前，应先检查现有编号表，避免重复编号或改变既有编号的含义。
